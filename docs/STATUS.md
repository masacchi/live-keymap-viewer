## 3. 分かっている制約

- **Bluetoothは未対応。調査と実装計画は[BLUETOOTH.md](BLUETOOTH.md)。** 分かっていること:
  - 実機のファームはRMK v0.8.xで、**USBとBLEのどちらか一方しか動かさない**。USBが出力先の
    あいだ、BT側のVialインターフェースは応答しない(2026-09-21に確認)
  - **BTだけの状態では、OSからはVialが答える**(2026-09-21に実測)
  - ただしBTの往復は実測で444〜488msと遅い。アプリは往復時間を覚えてタイムアウトを延ばす(P3)が、
    実機のBTではまだ試していない。選択画面では、名前とBluetoothの印で見分けられるようにした(P2)
- **USBとBTの両方で接続していると、同じキーボードのVialインターフェースが2つ見える。**
  VID/PIDが同じで見分けが付かず、出力先でない側は何も答えない。そこで各候補に`[0xFE, 0x00]`を送って
  確認し、答えるもののうち一番速いもの(両方答えるならUSB)を使う([hid/deviceProbe.ts](../src/renderer/src/hid/deviceProbe.ts))。
- **ノブの回転は表示できない。** QMKのエンコーダーはmatrixとは別の系統で、Vial / VIAにも
  回転を返すコマンドが無い。押し込みはmatrixのキーなので光る。
- **Combo / Key Override / One Shot / TTは再現していない。**
- **レイヤーの判定は近似。** Permissive Holdなどは再現していない。同じ20msのあいだに2つ押された
  キーは、行の若い順に押したものとして扱う(ARCHITECTURE.md §4)。
- **Vialコマンド(`0xFE`)の応答は照合できない。** 読み込み中やアンロック中にVialを操作すると、
  取り違える可能性がある。Vialを閉じて使うのが確実。
- **キーボードが消えたら(抜かれた・BTが切れた)、その場で切断して再接続に入る**
  (HIDの`disconnect`イベント)。
- **応答が15秒途切れると切断になる**(`STALL_LIMIT_MS`)。そこまでは「応答待ち…」のまま
  読み続ける。ウィンドウの枠をドラッグしているあいだなど、応答が一時的に返らないことがあり、
  短く切ると**ドラッグのたびに再接続**になるため。デバイスが消えた・書き込みに失敗したときは
  タイムアウトではないので、待たずに切る。再接続ではキーマップを丸ごと読み直すので数秒止まる。
  BTでは往復が450ms前後あるので、タイムアウトは往復時間の3倍(上限2秒)まで延びる([BLUETOOTH.md](BLUETOOTH.md) P3)。
- **モードを切り替えると再接続になる**(ウィンドウを作り直すため)が、**2回目からは待たない。**
  定義とキーマップをキャッシュしていて、身元を確かめる3往復で図が出る。キーマップが変わって
  いないかは裏で確認し、違っていれば差し替える(ARCHITECTURE.md §6)。初回と、ファームを
  書き換えて定義の大きさが変わったときだけ、全部(70〜96往復)読む。
- **Vialでキーマップを編集しても、自動では反映されない。** 「キーマップを読み直す」
  (デバイス名のメニュー。オーバーレイでは左上のパネル)を選ぶ。
- **定義(物理配置・カスタムキーの名前)はキャッシュしている。** ファームを書き換えたのに図や名前が
  古いままなら、「キーマップを読み直す」を選ぶ(定義もキャッシュを使わずに読み直す)。
- **TG / DFの状態は、アプリが押下から推測している。** アプリを起動する前や、切れていたあいだに
  押したものは分からない。
- 対応はVial protocol 6 / VIA protocol 9だけ。
