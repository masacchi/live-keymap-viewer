# Bluetooth 対応 — 調査結果と実装計画

2026-09-21 の調査のまとめ。**次のセッションでこれを読んで実装する**ためのもの。
結論を先に書き、根拠(ファームのソースの行番号、再現実験)をその後に置く。

---

## 0. 要約

1. **Cornix LP のファームは QMK ではなく RMK**(Rust 製)。docs/PROTOCOL.md は vial-qmk で
   確かめた内容なので、実機とは実装が別。USB で動いているので互換性は十分だが、細部が違う(§2.5)。
2. **RMK は USB と BLE のどちらか一方しか動かさない。** USB が出力先のあいだ、BT 側の
   Vial インターフェースには誰も答えない。2026-09-21 の「デバイスが応答しない」はこれが原因で、
   アプリ側は「答えるインターフェースを選ぶ」ように直してある(`hid/deviceProbe.ts`)。
3. **BT でも Vial は答える(OS レベルで確認済み)。** USB を抜いた状態で、Windows の HID API から
   BT 側の Vial インターフェースに問い合わせたら、vial_protocol 6 と正しい UID が返った(§2.6)。
   BLE 側の Vial の形(レポート ID 無し・32 バイト)もアプリの送り方と一致している。
4. **アプリの選択ダイアログでは「不明なデバイス(E118:0001)」と出る。** BT 経由では Windows が
   製品名を渡さないため。しかも VIA 用インターフェースを持つ別の機器(Keychron Link)も並ぶので、
   「Cornix が候補に無い」ように見える(§2.6、P2)。
5. **今のアプリは BT の遅さに耐えられない。** 実測の往復は **444〜488ms**(何もしていないとき)。
   RMK のスレーブレイテンシ 30 と接続間隔 15ms の組み合わせ(15ms × 31 ≈ 465ms)と一致する。
   matrix の時間切れ(200ms)どころか、**読み込みの時間切れ(500ms)にも届く**。この遅さを再現すると、
   押下が 1 回ずれて表示される・取りこぼす・止まる、が起きる(§3)。**実装の本題はここ(P3)。**

## 1. 何が起きたか

- USB で繋いでいたのに「デバイスが応答しない」が出た
- Windows のデバイス一覧に、Cornix の Vial インターフェース(「HID 準拠ベンダー定義デバイス」)が
  USB 側と BT(BLE)側に 1 つずつあった。BT のペアリングが残っていて、接続も生きていた
- 同じ VID/PID なので、アプリは両方を許可済みとして扱い、`getDevices()` の先頭(BT 側)を掴んでいた
- USB が出力先なので BT 側は答えず、全リクエストが時間切れになった

→ 修正済み(コミット `bdd53a2`)。候補が複数あれば `[0xFE, 0x00]` を投げて、答えるもののうち
一番速いものを使う。

## 2. 分かったこと(根拠つき)

### 2.1 ファームは RMK v0.8.x

Cornix LP V1.12 のファーム(`jezailfunder/cornix-lp` の `cornix固件 V1.12/cornix-left.uf2`)に
埋め込まれたパニック時のソースパスから分かる:

```
/Users/haobogu/Projects/keyboard/fix/cornix_panic/rmk/src/host/via/vial.rs
/Users/haobogu/Projects/keyboard/fix/cornix_panic/rmk/src/ble/mod.rs
.../trouble-host-0.5.1/src/...
.../embassy-nrf-0.8.0/src/usb/mod.rs
```

- RMK の作者(haobogu)本人がビルドしたもの。ブランチ名らしき `fix/cornix_panic` があり、
  Cornix 向けの手直しが入っている可能性はある(**正確なリビジョンは不明**)
- 依存の版(`trouble-host 0.5.1` / `embassy-nrf 0.8`)が一致するのは **RMK v0.8.1〜v0.8.3**。
  v0.9.0 からは `trouble-host 0.8` / `embassy-nrf 0.11` に変わる
- 以下の行番号は **`rmk-rs/rmk` のタグ `rmk-v0.8.3`** のもの

### 2.2 USB と BLE は同時には動かない

`rmk/src/ble/mod.rs` の 260 行目から。接続の種類(`get_connection_type()`)で分岐する:

| モード | 動き | 行 |
|---|---|---|
| USB 優先(`ConnectionType::Usb`) | USB が有効になるか BLE が繋がるのを待つ。**USB が有効なら USB のキーボードだけを動かす** | 261–297 |
| 〃(USB が無いとき) | 「No USB, BLE connected, run BLE keyboard」。BLE 側を動かす | 298–313 |
| BLE 優先(`ConnectionType::Ble`) | 広告しながら USB 側を動かし、**BLE が繋がったら BLE 側に切り替える** | 342–370 |

BLE 側の Vial は `run_ble_keyboard`(849 行目)の中の `BleHostServer::new(server, conn)`(870 行目)で
動く。USB 側を動かしているあいだはこれが走らないので、BT 側の Vial インターフェースに書いても
何も返らない。**Windows には BT 側のデバイスが「OK」で残る**ので、アプリからは見える。

出力先の切り替えは、キーマップの `USER06`(Cornix の customKeycodes で `SWITCH`
「Switch default output mode between USB/BLE」)。このユーザーのキーマップでは L4 の左上。
**USB ケーブルを抜けば**、USB 優先モードのまま BLE 側に落ちるので、そちらの方が試しやすい。

### 2.3 BLE 側の Vial の形は、アプリの送り方と一致している

`rmk/src/ble/host_service/vial.rs`:

- 独立した GATT の HID サービス(11 行目 `VialService`)。Windows ではこれが BT 側の
  「HID 準拠ベンダー定義デバイス」になる
- レポートマップは `ViaReport`(`rmk/src/descriptor.rs` 34 行目: usagePage `0xFF60` / usage `0x61`)。
  **レポート ID は付いていない**
- Report Reference 記述子は入力 `[0, 1]`、出力 `[0, 2]`(20・23 行目)= レポート ID 0
- 入力・出力とも **32 バイト**(22・25 行目)。応答は `input_data.notify`(51 行目)

アプリは `sendReport(0x00, 32 バイト)` で送り、`inputreport` を待つので、形の上では合っている。
**レポート ID を変える必要は無い。**

### 2.4 BLE の往復は遅い(最悪 240〜465ms)

`rmk/src/ble/mod.rs` 798 行目 `set_conn_params`:

| 時期 | 接続間隔 | スレーブレイテンシ | 最悪の待ち(間隔 ×(レイテンシ+1)) |
|---|---|---|---|
| 接続から 5 秒後〜10 秒 | 15ms(816–817 行) | 30(818 行) | 約 465ms |
| 10 秒以降 | 7.5ms(833–834 行) | 30(835 行) | 約 232ms |

スレーブレイテンシ 30 = キーボード側は送るものが無ければ最大 30 回ぶん受信を休める。
ホストからの要求はキーボードが起きるまで届かないので、**要求 1 回の往復が最悪これくらいかかる**。
打鍵中はキーボード側も送信で起きているので、もっと速いかもしれない(未計測)。

**実測(2026-09-21、接続から十分経ったあと、何もしていないとき):444ms と 488ms。**
7.5ms 間隔なら最悪 約 232ms のはずなので、**実際には 15ms 間隔のまま**と考えるのが自然
(15ms × 31 ≈ 465ms)。Windows が 7.5ms への変更を受け入れていない可能性がある。
**設計は「往復 500ms 前後」を前提にすること。**

これはファームの設定なので、アプリからは変えられない。

### 2.5 RMK の Vial 実装の、vial-qmk との違い

| 項目 | vial-qmk | RMK v0.8.3 | 影響 |
|---|---|---|---|
| matrix state | `data[2..]`、行ごと MSB バイトが先 | 同じ位置(`host/via/mod.rs` 130–142 行)。アンロック済みのときだけ返す | 無し(USB で動作確認済み) |
| アンロックのカウンタ | 50 から始まり、押し続けると 100ms ごとに 1 減る | **まだ押されていないアンロックキーの数**(`host/via/vial_lock.rs` 42–57 行)。全部押した瞬間に解除 | 進捗バーが最初から 96% 近くになる(アプリは最大値を 50 決め打ち)。§4 P4 |
| アンロック進行中の状態 | ファームにタイムアウトが無く、途中で閉じると残る | **最後のポーリングから 100ms で自動的に解ける**(`vial_lock.rs` 62–65 行) | RMK では「進行中のまま固まる」問題は起きない |
| アンロック進行中の VIA コマンド | 通さない(`via.c` 215–224 行) | `host/via/mod.rs` に止める処理は見当たらない | 無し |

### 2.6 Windows / Electron からの見え方(2026-09-21 実測)

USB を抜き、BT だけで繋いだ状態で調べた。道具は §8。

**Windows の HID API から直接(`npm run diag:hid`)**:

| インターフェース | UsagePage / Usage | レポート長(入 / 出) | 開けるか | `[0xFE, 0x00]` への応答 |
|---|---|---|---|---|
| BT の Vial(`...#d&36cabb35&0&0000`) | `FF60` / `61` | 33 / 33(32 + レポート ID) | 読み書き可 | **444〜488ms で `06 00 00 00` + UID** |
| BT のキーボード | `0001` / `06` | 9 / 2 | 不可(Windows が独占) | — |
| BT のマウス・メディア・システム | `0001/02`・`000C/01`・`0001/80` | — | — | — |

- 返ってきた UID `B9 BC 09 B2 9D 37 4C EA` は `.vil` の uid(16882930253541522617)と一致
- ハードウェア ID は USB 側と同じ `HID_DEVICE_UP:FF60_U:0061`
- **ファームも OS も、BT で Vial のやり取りができている。**

**Electron(WebHID)から(`npm run diag:webhid`)**。`select-hid-device` に渡ってくる一覧:

| 絞り込み | 並ぶもの |
|---|---|
| Vial(`0xFF60` / `0x61`) | `3434:D026` **Keychron Link-KM**、`E118:0001` **不明なデバイス(E118:0001)** |

- **BT の Cornix は Chromium にも見えている。** ただし名前が「不明なデバイス(E118:0001)」
  (BT 経由では製品名の文字列が取れず、Chromium が VID:PID で代用する)
- 別の機器 **Keychron Link-KM**(Keychron の無線レシーバー)も VIA 用インターフェースを持っていて並ぶ。
  VID/PID が違うので、アプリ(`main/hid.ts`)は「別々のキーボードが複数ある」と判断して
  選択ダイアログを出す。そこに「Cornix」という名前が無いので、**BT の Cornix が候補に無いように見える**
- Keychron Link に `[0xFE, 0x00]` を送ると **`0xFF`(`id_unhandled`)が返る** = VIA だけの機器で、
  Vial ではない。**この問い合わせで Vial かどうかを見分けられる**

## 3. 今のアプリは BT の遅さで壊れる(再現済み)

偽の HID デバイス(ファーム模擬の裏に遅延を入れたもの)で、`getMatrixState` を 4 回続けて呼んだ。
3 回目の直前にキーを押し、4 回目の直前に離している。正しければ 3 回目だけが「押」になる。

| 往復 | 1 回目 | 2 回目 | **3 回目(押)** | 4 回目(離) | 送った要求 |
|---|---|---|---|---|---|
| 60ms | 離 | 離 | **押** ✅ | 離 | 4 |
| 250ms | 離 | 離 | **離** ❌(36ms で返る) | **押** ❌ | 6 |
| 480ms | 離 | 離 | **離** ❌ | 離 | 6 |
| 650ms | **エラー**「デバイスが応答しない(コマンド 0x02 0x03)」 | | | | |

### なぜ起きるか

1. matrix の要求は時間切れ 200ms・3 回まで(`hid/vial.ts` の `getMatrixState`)
2. 往復が 200ms を超えると、同じ要求をもう一度送る
3. 最初の要求への応答が遅れて届く。**同じコマンドなので照合を通り**、再送した要求の応答として受け取る
4. 再送した要求への応答は、**次の回の応答として**受け取られる。以後ずっと 1 回ずつずれ、
   再送のたびにずれが増える
5. 往復が 200ms × 3 = 600ms を超えると、3 回とも間に合わずエラーになる。
   `KeyboardSession` はエラーでポーリングを止める

VIA / Vial には要求と応答を対応づける番号が無いので、**照合(`SendOptions.validate`)では防げない**。

読み込み(`LONG` = 時間切れ 500ms・20 回)も同じ理屈で、往復が 500ms を超えると再送が起きる。
`0x12`(keymap)はオフセットまで照合するのでずれないが、**`0xFE` 系(定義ブロックなど)は照合が
無いので、ずれると定義の XZ 展開が壊れる**。**実測の往復 444〜488ms は、この 500ms のすぐ下**で、
少し遅れれば読み込みの段階から壊れ得る。

## 4. 実装計画

優先度順。P3 が本題。P1 は OS レベルまで済んでいる。

### P1. 実機で「BT だけ」の状態を試す(コードを書く前に)— **OS レベルでは済み**

OS レベルでは答えることを確かめた(§2.6)。残りは**アプリで**どうなるか。
**選択ダイアログでは「不明なデバイス(E118:0001)」を選ぶ**(それが BT の Cornix)。
今のビルドのままでよい。時間切れのメッセージにコマンドが出るようにしてあるので、それで切り分ける。

1. Vial / Pipette を閉じる
2. **USB ケーブルを抜く**(キーボードは電池で動く。USB 優先モードのまま BLE 側に落ちる)
3. BT で普通に文字が打てることを確かめる
4. アプリを起動する。候補は BT 側の 1 つだけなので、そのまま繋ぎに行く
5. 結果で分岐する:

| 見えたもの | 意味 | 次 |
|---|---|---|
| 読み込めて、アンロック後に押下が光る | BT で動く。ただし遅れやずれは §3 のとおり出るはず | P2 へ |
| 「デバイスが応答しない(コマンド 0x02 0x03)」 | 読み込みは通り、matrix のポーリングで時間切れ | P2 へ |
| 「デバイスが応答しない(コマンド 0x01)」など最初の要求で止まる | BT 側の Vial に全く届いていない | §5 の未解決事項を調べる |
| キーボードが BT で繋がらない | ペアリングの問題 | Windows の設定から繋ぎ直す |
| 読み込みの途中で XZ の展開エラー | 往復が 500ms を超えて定義ブロックがずれた(§3) | P3 へ |

**結果は STATUS.md §1 と README の「接続の確認状況」に書く。**

### P2. 選択ダイアログで BT の Cornix を分かるようにする

§2.6 のとおり、今は「不明なデバイス(E118:0001)」と Keychron Link が並び、Cornix だと分からない。

- **名前の無いデバイスに、覚えている名前を付けて出す。** `settings.json` の `grantedDevices` には、
  USB で最初に繋いだときの名前が VID/PID ごとに残っている(`main/hid.ts` の `rememberDevice`)。
  同じ VID/PID で名前が「不明なデバイス…」なら、その名前に「(名前なし・Bluetooth の可能性)」を添える。
  名前が無いかどうかは、Chromium の文言に頼らず「覚えている名前と違い、VID:PID を含む」くらいで判定する
- **以前許可した VID/PID があれば、ダイアログを出さずにそれを選ぶ。** HANDOFF §3
  「以前許可したデバイスには自動で再接続する」にも沿う。許可済みが複数あるとき・無いときだけ選ばせる
- **Vial でない機器を見分ける。** Keychron Link のような VIA だけの機器は `[0xFE, 0x00]` に `0xFF` を
  返す(§2.6)。`hid/deviceProbe.ts` の確かめで、応答の `data[0] === 0xFF` なら「答えたが Vial ではない」
  として候補から外す。選択ダイアログは main が出すので、renderer で確かめた結果を使うなら、
  確かめてから renderer 側で選ばせる形に寄せる(main は許可だけ出す)方が素直
- テスト: `tests/main/main.test.ts` の `HidPermissions`、`tests/webhidTransport.test.ts` の選び方

### P3. 往復時間に合わせて時間切れを伸ばし、ずれを防ぐ

目標: 往復 **700ms 程度まで**(実測 444〜488ms に余裕を見て)、読み込みが壊れず、押下を**正しい回に**
読める。遅くてもよいが、ずれない・止まらない。

**(a) 時間切れを実測の往復時間から決める**(主策)

- `WebHidTransport` が往復時間を記録する(直近の最大値、または指数移動平均 + 余裕)
- 呼び出し側が渡す `timeoutMs` は「最低値」として扱い、実際の時間切れは
  `max(timeoutMs, 観測した往復 × 3)` くらいにする。上限は 2 秒程度。**実測 450〜490ms なので、
  BT では時間切れが 1.5 秒前後になる**
- 最初の 1 回は測れないので、接続直後の `[0xFE, 0x00]`(`deviceProbe.ts` で既に測っている)を
  初期値に使う。候補が 1 つのときは今は確かめを飛ばしているので、**1 回だけ測る**ようにする
- こうすれば、普段は再送が起きず、§3 のずれそのものが起きない

**(b) 取り残された応答を捨てる**(保険)— **2026-09-23 に実装済み**

`WebHidTransport` が「時間切れで諦めた要求の数」(`abandoned`)を数え、届いた応答をその数だけ捨てる。
応答ごと失われた場合に数え続けないよう、2 秒の窓(`STALE_RESPONSE_WINDOW_MS`)を過ぎたら数え直す。
テストは `tests/webhidTransport.test.ts` の「時間切れのあとの取り違え」。
**スキップしたままの BLE のテストが通るには (a) が要る** ― 往復 250ms に対して時間切れが 200ms では、
何回投げ直しても間に合わないため。

以下は実装時のメモ。

時間切れが起きたときのために、`WebHidTransport` で「送ったがまだ応答が来ていない要求の数」を数える。
応答が来たとき、未応答が 2 つ以上なら、それは**前に諦めた要求への応答**なので捨てて数を減らす。
1 つになったものだけを今の要求の応答として受け取る。

- 要求そのものが失われた場合は数が減らなくなるので、長く(例えば 2 秒)何も来なければ 0 に戻す
- (a) だけでも普段は足りるはず。(b) は BLE の一時的な詰まりでずれが残らないようにするため

**(c) ポーリングの間隔**

`KeyboardSession.runPolling` は「1 往復 → 20ms の残りを待つ」なので、往復が 20ms を超えれば
自然に往復の速さで回る。変更は要らない。

**テスト**: `tests/webhidTransport.test.ts` の `FirmwareBackedDevice` には `latencyMs` があるので、
§3 の実験をそのままテストにできる。スキップしたテストとして置いてある
(`BLE 並みの往復でも、押したキーを正しい回に読む`)。**P3 を実装したらスキップを外し、通ること。**
実測に合わせて、遅延を 250ms から **500ms** に上げたケースも足すとよい。
読み込み全体を 250ms で回すと 95 往復 × 250ms ≈ 24 秒かかるので、テストは matrix だけにする。

読み込みの往復は 2026-09-21 に減らした(Tap Dance は使う枠と先頭 5 個だけ、定義はキャッシュ)。
モックで数えて、初回 95 往復、定義がキャッシュにあれば 71 往復。BT の 470ms なら約 45 秒と 33 秒。

**2026-09-23 追記: キーマップもキャッシュした**(`hid/keymapCache.ts`)。2 回目からは身元を
確かめる **3 往復**(BT で約 1.5 秒)で図が出て、押下のポーリングもすぐ始まる。読み直しは裏で走る。
つまり **BT で待たされるのは初回だけ**になったので、P3 で直すべきは「遅くても壊れないこと」に絞ってよい。
ただし裏の読み直しは matrix のポーリングと同じキューに並ぶので、**取り違え(P3(b))の影響を受ける
場面が増えている**。P3(b) を先に入れるのが安全。

### P4. 出力先の切り替えや抜き差しに追従する — **繋ぎ直しの土台は済み**

2026-09-21 に `session/keyboardConnection.ts` を入れた。一度でも動いた実機のセッションが
error になったら、2 秒ごとに許可済みのデバイスを探し直して `connectToResponsive` で繋ぐ。
`navigator.hid` の `connect` イベントが来たら待たずに試す(`disconnect` イベントは聞いていない。
使っていたデバイスが消えればセッションが通信に失敗して error になるので、それで足りる)。

残っていること:

- `SWITCH` で出力先を変えたときに、実機で追従するか確かめる。USB → BT は P3 が入るまで
  遅さで読み込みに失敗するはず
- 出力先を切り替えた直後は、新しい側が答え始めるまで少しかかるはず(実測)
- アンロックは接続し直すたびに要るかもしれない(RMK の `VialLock` は再起動で消える。
  USB ⇄ BLE の切り替えで消えるかは未確認)

### P5. アンロックの進捗を RMK に合わせる

RMK のカウンタは「まだ押されていないキーの数」(§2.5)なので、アプリの最大値 50 決め打ちだと
進捗バーが最初から 96% 付近になる。vial-gui と同じく、**最大値を「これまでに見たカウンタの最大値」**
にする(`unlocker.py` の `self.progress.setMaximum(max(self.progress.maximum(), unlock_counter))`)。
vial-qmk(50 から減る)と RMK(キーの数から減る)の両方で正しく出る。

- `session/keyboardSession.ts` の `UnlockState.max` を、最初は `VIAL_UNLOCK_COUNTER_MAX` ではなく
  最初に見た `counter` にし、以後は大きい方を取る
- モック(`MockTransport`)は vial-qmk 流なので、RMK 流のモードを足すとテストしやすい

### P6. 接続の様子を画面に出す(診断用)

BT は遅さが問題になるので、ツールバーに「往復 12ms」のような表示があると切り分けが早い。
P3 で往復時間を記録するので、それを出すだけ。WebHID からは USB か BT かは分からないので、
往復時間で見分ける(USB は数 ms、BT は十数 ms 以上)。

### P7. (P1 の結果しだい)BT で matrix が実用にならない場合

往復 450ms では 1 秒に 2 回ほどしか読めず、速い打鍵は取りこぼす。それで足りなければ、HANDOFF §3 で
「MVP の対象外」にした**キー入力からの推測表示**(OS に届いたキーから押下を推測する)を検討する。
ファームを触れるなら、スレーブレイテンシを下げる・押下イベントを通知で送らせる、の方が素直。

## 5. 分かっていないこと

- ~~出力先を BT にしたとき、実際に答えるか~~ → **OS レベルでは答える**(§2.6)。アプリでの結果は未確認
- 打鍵中など、キーボード側が起きているときの往復時間。スレーブレイテンシは送るものが無いときだけ
  効くので、ポーリングし続けていれば速くなる可能性がある(`npm run diag:hid` は 1 回しか測らない)
- 接続間隔が 7.5ms に下がっていない理由(Windows が拒否しているのか、Cornix 版のファームが違うのか)
- Cornix のファームに RMK v0.8.3 から外れた変更があるか(`fix/cornix_panic` の中身)
- USB ⇄ BT を切り替えたとき、アンロックが解けるか(RMK の `VialLock` は再起動で消える)
- HANDOFF の「BT でも Vial で読み取れる」— Vial 本体(hidapi)でも同じ遅さになっているはず。
  Vial 本体は読み込みの時間切れが 500ms・再送 20 回(`util.py` の `hid_send`)で、アプリと同じ
  ずれの危険を抱えている。Vial 本体で問題が出ていないなら、実際の往復はもっと短い時間帯があるのかもしれない

## 8. 診断の道具

どちらも WSL から Windows 側を調べる。**アプリの動作には触らない**(アプリを終了させる必要も無い)。

| コマンド | 何が分かるか | 触るもの |
|---|---|---|
| `npm run diag:hid` | Windows の HID API から見た Cornix のインターフェース(用途・レポート長・開けるか)と、Vial の `[0xFE, 0x00]` への応答と往復時間。**Chromium を通さない**ので、「OS では動くのにアプリで駄目」を切り分けられる | Vial のインターフェースに `[0xFE, 0x00]` を 1 回送る(アプリが接続時に最初に送るのと同じ) |
| `npm run diag:hid -- 3434` | 別の VID の機器(例: Keychron)。`0xFF` が返れば VIA だけの機器 | 同上 |
| `npm run diag:webhid` | Electron(WebHID)の `select-hid-device` に何が並ぶか・名前がどう出るか。選択ダイアログの中身そのもの | 何も開かない。Windows の `%TEMP%` に診断用アプリを一時的に置いて、ウィンドウを出さずに動かし、終わったら消す。先に `npm run package:win` が要る |

注意:

- `scripts/diag/hid-probe.ps1` は **BOM 付き UTF-8** で保存すること。Windows PowerShell 5.1 は BOM が
  無いと Shift_JIS として読み、日本語のコメントが化けて `param(...)` を巻き込み、引数が空になる
- `diag:webhid` の診断アプリは exe 名を変えてある(`LkvWebHidDiag.exe`)。本物と同じ名前だと、
  `deploy:win` の「起動中か」の判定に引っかかるため
