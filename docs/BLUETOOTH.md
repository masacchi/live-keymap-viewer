# Bluetooth対応 — 調査結果と実装計画

Bluetooth(BT)で使えるようにするための調査結果と、実装の計画。調べたのは2026-09-21。
結論を先に書き、根拠(ファームのソースの行番号、再現実験)をその後に置く。

---

## 0. 要約

1. **Cornix LPのファームはQMKではなくRMK**(Rust製)。docs/PROTOCOL.mdはvial-qmkで
   確認した内容なので、実機とは実装が別。USBで動いているので互換性は十分だが、細部が違う(§2.5)。
2. **RMKはUSBとBLEのどちらか一方しか動かさない。** USBが出力先のあいだ、BT側の
   Vialインターフェースには誰も答えない。「デバイスが応答しない」はこれが原因だったので、
   アプリは答えるインターフェースを選ぶようにしてある(`hid/deviceProbe.ts`)。
3. **BTでもVialは答える(OSから確認済み)。** USBを抜いた状態で、WindowsのHID APIから
   BT側のVialインターフェースに問い合わせたら、vial_protocol 6と正しいUIDが返った(§2.6)。
   BLE側のVialの形(レポートID無し・32バイト)も、アプリの送り方と一致している。
4. **BT経由では製品名が取れないことがある。** ChromiumのWebHIDでは「不明なデバイス(E118:0001)」と出た。
   しかもVIA用のインターフェースを持つ別の機器(Keychron Link)も並ぶので、
   「Cornixが候補に無い」ように見える(§2.6、P2)。
5. **BTの往復は遅い。** 実測の往復は**444〜488ms**(何もしていないとき)。
   RMKのスレーブレイテンシ30と接続間隔15msの組み合わせ(15ms × 31 ≈ 465ms)と一致する。
   matrixのタイムアウト(200ms)どころか、**読み込みのタイムアウト(500ms)にも届く**。タイムアウトを
   固定にすると、押下が1回ずれて表示される・取りこぼす・止まる、が起きる(§3)。アプリは往復時間を
   覚えてタイムアウトを延ばす(P3、対応済み。モックの遅延で確認し、実機では未確認)

> アプリのHIDはRustのhidapi(WindowsのHID API)で扱う(ARCHITECTURE.md §2)。§2.6のWebHIDでの
> 見え方は、Chromiumを通したときのもの。hidapiではデバイスのパスが取れるので、USBかBTかはパスで分かる
> (BTは`{00001812-…}`を含む)。往復・タイムアウト・照合は画面の側のTypeScript(`transport.ts`)にあるので、
> §3の問題とP3はそのまま当てはまる。

## 1. 何が起きたか

- USBで接続していたのに「デバイスが応答しない」が出た
- Windowsのデバイス一覧に、CornixのVialインターフェース(「HID準拠ベンダー定義デバイス」)が
  USB側とBT(BLE)側に1つずつあった。BTのペアリングが残っていて、接続も生きていた
- 同じVID/PIDなので、アプリは両方を許可済みとして扱い、一覧の先頭(BT側)を選んでいた
- USBが出力先なのでBT側は答えず、全リクエストがタイムアウトした

→ 修正済み。候補が複数あれば`[0xFE, 0x00]`を送って、答えるもののうち一番速いものを使う。

## 2. 分かったこと(根拠つき)

### 2.1 ファームはRMK v0.8.x

Cornix LP V1.12のファーム(`jezailfunder/cornix-lp`の`cornix固件 V1.12/cornix-left.uf2`)に
埋め込まれた、パニック時のソースパスから分かる。

```
/Users/haobogu/Projects/keyboard/fix/cornix_panic/rmk/src/host/via/vial.rs
/Users/haobogu/Projects/keyboard/fix/cornix_panic/rmk/src/ble/mod.rs
.../trouble-host-0.5.1/src/...
.../embassy-nrf-0.8.0/src/usb/mod.rs
```

- RMKの作者(haobogu)本人がビルドしたもの。ブランチ名らしき`fix/cornix_panic`があり、
  Cornix向けの手直しが入っている可能性はある(**正確なリビジョンは不明**)
- 依存の版(`trouble-host 0.5.1` / `embassy-nrf 0.8`)が一致するのは**RMK v0.8.1〜v0.8.3**。
  v0.9.0からは`trouble-host 0.8` / `embassy-nrf 0.11`に変わる
- 以下の行番号は、**`rmk-rs/rmk`のタグ`rmk-v0.8.3`のもの**

### 2.2 USBとBLEは同時には動かない

`rmk/src/ble/mod.rs`の260行目から。接続の種類(`get_connection_type()`)で分岐する。

| モード | 動き | 行 |
|---|---|---|
| USB優先(`ConnectionType::Usb`) | USBが有効になるかBLEが接続されるのを待つ。**USBが有効ならUSBのキーボードだけを動かす** | 261–297 |
| 〃(USBが無いとき) | 「No USB, BLE connected, run BLE keyboard」。BLE側を動かす | 298–313 |
| BLE優先(`ConnectionType::Ble`) | 広告しながらUSB側を動かし、**BLEが接続されたらBLE側に切り替える** | 342–370 |

BLE側のVialは、`run_ble_keyboard`(849行目)の中の`BleHostServer::new(server, conn)`(870行目)で
動く。USB側を動かしているあいだはこれが走らないので、BT側のVialインターフェースに書いても
何も返らない。**WindowsにはBT側のデバイスが「OK」のまま残る**ので、アプリからは見える。

出力先の切り替えは、キーマップの`USER06`(Cornixのcustom keycodesで`SWITCH`、
「Switch default output mode between USB/BLE」)。このユーザーのキーマップではL4の左上。
**USBケーブルを抜けば**、USB優先モードのままBLE側に切り替わるので、そちらの方が試しやすい。

### 2.3 BLE側のVialの形は、アプリの送り方と一致している

`rmk/src/ble/host_service/vial.rs`:

- 独立したGATTのHIDサービス(11行目`VialService`)。WindowsではこれがBT側の
  「HID準拠ベンダー定義デバイス」になる
- レポートマップは`ViaReport`(`rmk/src/descriptor.rs` 34行目: usagePage `0xFF60` / usage `0x61`)。
  **レポートIDは付いていない**
- Report Reference記述子は、入力`[0, 1]`、出力`[0, 2]`(20・23行目)= レポートID 0
- 入力・出力とも**32バイト**(22・25行目)。応答は`input_data.notify`(51行目)

アプリはレポートID 0で32バイトを送り、入力レポートを待つので、形の上では合っている。
**レポートIDを変える必要は無い。**

### 2.4 BLEの往復は遅い(最悪240〜465ms)

`rmk/src/ble/mod.rs` 798行目`set_conn_params`:

| 時期 | 接続間隔 | スレーブレイテンシ | 最悪の待ち(間隔 ×(レイテンシ+1)) |
|---|---|---|---|
| 接続から5秒後〜10秒 | 15ms(816–817行) | 30(818行) | 約465ms |
| 10秒以降 | 7.5ms(833–834行) | 30(835行) | 約232ms |

スレーブレイテンシ30とは、キーボード側は送るものが無ければ、最大30回ぶん受信を休めるということ。
ホストからの要求はキーボードが起きるまで届かないので、**要求1回の往復が最悪これくらいかかる**。
打鍵中はキーボード側も送信で起きているので、もっと速いかもしれない(未計測)。

**実測(2026-09-21、接続から十分経ったあと、何もしていないとき):444msと488ms。**
7.5ms間隔なら最悪で約232msのはずなので、**実際には15ms間隔のまま**と考えるのが自然
(15ms × 31 ≈ 465ms)。Windowsが7.5msへの変更を受け入れていない可能性がある。
**設計は「往復500ms前後」を前提にすること。**

これはファームの設定なので、アプリからは変えられない。

### 2.5 RMKのVial実装の、vial-qmkとの違い

| 項目 | vial-qmk | RMK v0.8.3 | 影響 |
|---|---|---|---|
| matrix state | `data[2..]`、行ごとにMSBのバイトが先 | 同じ位置(`host/via/mod.rs` 130–142行)。アンロック済みのときだけ返す | 無し(USBで動作を確認済み) |
| アンロックのカウンタ | 50から始まり、押し続けると100msごとに1減る | **まだ押されていないアンロックキーの数**(`host/via/vial_lock.rs` 42–57行)。全部押した瞬間に解除 | バーの最大値を決め打ちできない。アプリは見たカウンタの最大値を最大にする(§4 P5、対応済み) |
| アンロック進行中の状態 | ファームにタイムアウトが無く、途中で閉じると残る | **最後のポーリングから100msで自動的に解ける**(`vial_lock.rs` 62–65行) | RMKでは「進行中のまま固まる」問題は起きない |
| アンロック進行中のVIAコマンド | 通さない(`via.c` 215–224行) | `host/via/mod.rs`に止める処理は見当たらない | 無し |

### 2.6 WindowsとChromiumからの見え方(2026-09-21実測)

USBを抜き、BTだけで接続した状態で調べた。道具は§8。

**WindowsのHID APIから直接(`npm run diag:hid`)**:

| インターフェース | UsagePage / Usage | レポート長(入 / 出) | 開けるか | `[0xFE, 0x00]`への応答 |
|---|---|---|---|---|
| BTのVial(`...#d&36cabb35&0&0000`) | `FF60` / `61` | 33 / 33(32 + レポートID) | 読み書きできる | **444〜488msで`06 00 00 00` + UID** |
| BTのキーボード | `0001` / `06` | 9 / 2 | 開けない(Windowsが独占) | — |
| BTのマウス・メディア・システム | `0001/02`・`000C/01`・`0001/80` | — | — | — |

- 返ってきたUID `B9 BC 09 B2 9D 37 4C EA`は、`.vil`のuid(16882930253541522617)と一致
- ハードウェアIDはUSB側と同じ`HID_DEVICE_UP:FF60_U:0061`
- **ファームもOSも、BTでVialのやり取りができている。**

**ChromiumのWebHIDから**。Vial(`0xFF60` / `0x61`)で絞り込んだ候補に並んだもの:

| 並んだもの | 中身 |
|---|---|
| `3434:D026` **Keychron Link-KM** | Keychronの無線レシーバー。VIA用のインターフェースを持っている |
| `E118:0001` **不明なデバイス(E118:0001)** | BTのCornix。BT経由では製品名の文字列が取れず、ChromiumがVID:PIDで代用した |

- **BTのCornixは見えている。** ただし名前が無い
- Keychron Link-KMもVIA用のインターフェースを持っていて並ぶ。VID/PIDが違うので、アプリ
  (`hid/nativeHid.ts`の`requestDevice`)は「別々のキーボードが複数ある」と判断して選択画面を出す。
  そこに「Cornix」という名前が無いので、**BTのCornixが候補に無いように見える**
- Keychron Linkに`[0xFE, 0x00]`を送ると、**`0xFF`(`id_unhandled`)が返る** = VIAだけの機器で、
  Vialではない。**この問い合わせで、Vialかどうかを見分けられる**

## 3. タイムアウトが固定だと、BTの遅さで壊れる(再現済み。P3で対応済み)

偽のHIDデバイス(ファームの模擬の裏に遅延を入れたもの)で、`getMatrixState`を4回続けて呼んだ。
3回目の直前にキーを押し、4回目の直前に離している。正しければ3回目だけが「押」になる。
下の表はタイムアウトを固定(matrixは200ms × 3回)にしたときの結果。いまはP3(a)で往復に合わせて
延ばすので、250ms・500msのどちらでも正しく読める(`tests/bluetoothLatency.test.ts`)。

| 往復 | 1回目 | 2回目 | **3回目(押)** | 4回目(離) | 送った要求 |
|---|---|---|---|---|---|
| 60ms | 離 | 離 | **押** ✅ | 離 | 4 |
| 250ms | 離 | 離 | **離** ❌(36msで返る) | **押** ❌ | 6 |
| 480ms | 離 | 離 | **離** ❌ | 離 | 6 |
| 650ms | **エラー**「デバイスが応答しない(コマンド0x02 0x03)」 | | | | |

### なぜ起きるか

1. matrixの要求は、タイムアウト200ms・3回まで(`hid/vial.ts`の`getMatrixState`)
2. 往復が200msを超えると、同じ要求をもう一度送る
3. 最初の要求への応答が遅れて届く。**同じコマンドなので照合を通り**、送り直した要求の応答として受け取る
4. 送り直した要求への応答は、**次の回の応答として**受け取られる。以後ずっと1回ずつずれ、
   送り直すたびにずれが増える
5. 往復が200ms × 3 = 600msを超えると、3回とも間に合わずエラーになる。
   `KeyboardSession`はエラーでポーリングを止める

VIA / Vialには要求と応答を対応づける番号が無いので、**照合(`SendOptions.validate`)では防げない**。

読み込み(`LONG` = タイムアウト500ms・20回)も同じ理屈で、往復が500msを超えると送り直しが起きる。
`0x12`(keymap)はオフセットまで照合するのでずれないが、**`0xFE`系(定義ブロックなど)は照合が
無いので、ずれると定義のXZ展開が壊れる**。**実測の往復444〜488msは、この500msのすぐ下**で、
少し遅れれば読み込みの段階から壊れ得る。

## 4. 実装計画

優先度の順。P1はOSからの確認まで、P2・P3・P5は済んでいる(P2・P3は実機では未確認)。

### P1. 実機で「BTだけ」の状態を試す(コードを書く前に)— **OSからの確認は済み**

OSからは答えることを確認した(§2.6)。残りは**アプリで**どうなるか。
選択画面にCornixの名前が無ければ、**名前の無いもの(VID:PIDが`e118:0001`)を選ぶ**(それがBTのCornix)。
いまのビルドのままでよい。タイムアウトのメッセージにコマンドが出るようにしてあるので、それで切り分ける。

1. Vial / Pipetteを閉じる
2. **USBケーブルを抜く**(キーボードは電池で動く。USB優先モードのままBLE側に切り替わる)
3. BTで普通に文字が打てることを確かめる
4. アプリを起動する。候補はBT側の1つだけなので、そのまま接続しに行く
5. 結果で分岐する

| 見えたもの | 意味 | 次 |
|---|---|---|
| 読み込めて、アンロック後に押下が光る | BTで動く。ただし遅れやずれは§3のとおり出るはず | P2へ |
| 「デバイスが応答しない(コマンド0x02 0x03)」 | 読み込みは通り、matrixのポーリングでタイムアウト | P2へ |
| 「デバイスが応答しない(コマンド0x01)」など、最初の要求で止まる | BT側のVialに全く届いていない | §5の分かっていないことを調べる |
| キーボードがBTで接続されない | ペアリングの問題 | Windowsの設定から接続し直す |
| 読み込みの途中でXZの展開エラー | 往復が500msを超えて定義ブロックがずれた(§3) | P3へ |

**結果はSTATUS.md §1とREADMEの「接続の確認状況」に書く。**

### P2. 選択画面でBTのCornixが分かるようにする — **済み**(実機では未確認)

§2.6のとおり、名前の無いデバイスとKeychron Linkが並び、どれがCornixか分からない。

- **名前の無いデバイスに、覚えている名前を付けて出す。** `settings.json`の`grantedDevices`には、
  許可したときの名前がVID/PIDごとに残っている。Rustが一覧を返すとき(`commands.rs`の`hid_devices`)、
  名前が空なら覚えている名前で補う。選択画面にもツールバーのデバイス名にも効く。BTで先に許可して名前が
  空のまま覚えたものは、あとでUSBで選んだときに名前を埋める(`settings.rs`の`remember_device`)
- **Bluetoothかどうかはパスで分かる**ので、推測ではなく「Bluetooth」の印を付ける(`hid.rs`の
  `is_bluetooth_path`。パスにHID over GATTのサービス`{00001812-…}`を含む)
- **前に接続したキーボードは、先頭に並べて「前回のキーボード」の印を付ける。自動では選ばない。**
  名前と印で見分けられれば選択画面でも迷わず、自動で選ぶと、別のキーボードに接続したいときに
  先に「忘れる」を押さないと選べなくなるため。選択画面を出すのは、これまでどおり別々のキーボード
  (VID/PIDが違うもの)が並ぶときだけ
- **Vialでない機器を見分ける。** Keychron LinkのようなVIAだけの機器は、`[0xFE, 0x00]`に`0xFF`
  (id_unhandled)を返す(§2.6)。接続前の確認(`hid/deviceProbe.ts`)で、答えても`data[0] === 0xFF`なら
  選ばない。Vialでない機器しか答えなければ、「応答しません」ではなく「Vialに対応していません」と出す。
  選択画面を出す前には問い合わせない(そのとき別のウィンドウや前のセッションがデバイスを使っている
  ことがあり、確認のために開くと応答が混ざる)
- テスト: `tests/nativeHid.test.ts`(並べ方・印・名前)、`tests/webhidTransport.test.ts`(Vialでない機器)、
  `tests/keyboardConnection.test.ts`(文言)、`src-tauri/src/hid.rs` / `settings.rs`のテスト

### P3. 往復時間に合わせてタイムアウトを延ばし、ずれを防ぐ

目標: 往復**700ms程度まで**(実測444〜488msに余裕を見て)、読み込みが壊れず、押下を**正しい回に**
読めること。遅くてもよいが、ずれない・止まらない。

**(a) タイムアウトを実測の往復時間から決める**(主な対策)— **実装済み**

- `WebHidTransport`が往復時間を覚える。長くなったらすぐその値に、短くなったら1割ずつ寄せる
  (一瞬の詰まりで延びたタイムアウトは、速い応答が続くうちに戻る)
- 呼び出し側が渡す`timeoutMs`は「最低値」として扱い、実際のタイムアウトは
  `max(timeoutMs, 覚えた往復 × 3)`、上限2秒(`timeoutFor`)。**実測が450〜490msなので、
  BTではタイムアウトが1.5秒前後になる**。USB(数ms)では呼び出し側の値のまま
- **最初の1回の往復は、タイムアウトして捨てる応答から測る。** 捨てる応答も「送った時刻」を覚えて
  おけば往復時間が分かる。分かった時点で、待っている要求(送り直した方)の期限も延ばす。そのため
  初期値を別に測って渡さなくても、1回の呼び出しの中で追いつく(接続前の確認`deviceProbe.ts`も、
  300msの待ちより往復が長いBTのCornixを、答えるものとして選べる)
- 答えないデバイスは往復時間が測れないので、待つ時間は延びない(答えない候補の確認が遅くならない)
- こうすれば、ふだんは送り直しが起きず、§3のずれそのものが起きない

**(b) 取り残された応答を捨てる**(保険)— **実装済み**

`WebHidTransport`が、タイムアウトで諦めた要求の数(`abandoned`)を数え、届いた応答をその数だけ捨てる。
応答ごと失われた場合に数え続けないよう、2秒の窓(`STALE_RESPONSE_WINDOW_MS`)を過ぎたら数え直す。
テストは`tests/webhidTransport.test.ts`の「時間切れのあとの取り違え」。
(b)だけでは往復がタイムアウトより長いときに読めない(何回送り直しても間に合わない)ので、(a)と組み合わせる。

**(c) ポーリングの間隔**

`KeyboardSession.runPolling`は「1往復 → 20msの残りを待つ」なので、往復が20msを超えれば
自然に往復の速さで回る。変更は要らない。

**テスト**: `tests/bluetoothLatency.test.ts`。`FirmwareBackedDevice`の`latencyMs`で
§3の実験をそのまま再現し、往復250ms・500msで押したキーを正しい回に読むこと、USB並みならタイムアウトが
変わらないこと、答えないデバイスでは延ばさないこと、詰まりのあとで戻ることを確かめる。
読み込み全体を250msで回すと95往復 × 250ms ≈ 24秒かかるので、テストはmatrixだけにする。

読み込みの往復は減らしてある(Tap Danceは使う枠と先頭5個だけ、定義とキーマップはキャッシュ)。
モックで数えると、初回は95往復、定義がキャッシュにあれば71往復で、BTの470msならそれぞれ約45秒と33秒。
キーマップもキャッシュにあれば、2回目からは身元を確かめる**3往復**(BTで約1.5秒)で図が出て、押下の
ポーリングもすぐ始まる。読み直しは裏で走る。つまり**BTで待たされるのは初回だけ**なので、P3で直すべきは
「遅くても壊れないこと」に絞ってよい。ただし裏の読み直しはmatrixのポーリングと同じキューに並ぶので、
取り違え(P3(b))の影響を受ける場面は多い。

### P4. 出力先の切り替えや抜き差しに追従する — **再接続の土台は済み**

`session/keyboardConnection.ts`が、一度でも動いた実機のセッションがerrorになったら、2秒ごとに
許可済みのデバイスを探し直して`connectToResponsive`で接続する。HIDの`connect`イベントが来たら待たずに試し、
使っていたデバイスの`disconnect`イベントが来たら、その場で切断して再接続に入る。

残っていること:

- `SWITCH`で出力先を変えたときに、実機で追従するかを確かめる。USB → BTは、P3が入るまで
  遅さで読み込みに失敗するはず
- 出力先を切り替えた直後は、新しい側が答え始めるまで少しかかるはず(要実測)
- アンロックは、接続し直すたびに要るかもしれない(RMKの`VialLock`は再起動で消える。
  USB ⇄ BLEの切り替えで消えるかは未確認)

### P5. アンロックの進み具合をRMKに合わせる — **済み**

RMKのカウンタは「まだ押されていないキーの数」(§2.5)なので、最大値を50に決め打ちすると、
進み具合のバーが最初から96%付近になる。vial-guiと同じく、**最大値を「これまでに見たカウンタの最大値」**
にしている(`unlocker.py`の`self.progress.setMaximum(max(self.progress.maximum(), unlock_counter))`)。
vial-qmk(50から減る)とRMK(キーの数から減る)の両方で正しく出る。

- `session/keyboardSession.ts`の`UnlockState.max`は、ポーリングする前は0(バーは空)、以後は見た`counter`の大きい方
- `MockTransport`の`firmware: 'rmk'`で、RMKと同じバイト並びで答える。RMKはポーリングの応答に状態を
  詰めてからカウンタを数える(`vial.rs` 95–105行)ので、全部押した回は「カウンタ0・まだロック中」で、
  アンロック済みと返るのは次のポーリング。アプリはこの回を「待つ」と扱うので、1回(200ms)遅れて終わる
- テスト: `tests/vial.test.ts`と`tests/keyboardSession.test.ts`の「RMKでは」

### P6. 接続の様子を画面に出す(診断用)

BTでは遅さが問題になるので、ツールバーに「往復12ms」のような表示があると切り分けが早い。
P3で往復時間を記録するので、それを出すだけ。USBかBTかは、hidapiのデバイスのパスで分かる
(BTは`{00001812-…}`を含む)。往復時間でも見分けられる(USBは数ms、BTは十数ms以上)。

### P7. (P1の結果しだい)BTでmatrixが実用にならない場合

往復450msでは1秒に2回ほどしか読めず、速い打鍵は取りこぼす。それで足りなければ、
**キー入力からの推測表示**(OSに届いたキーから押下を推測する)を検討する。
ファームを触れるなら、スレーブレイテンシを下げる・押下のイベントを通知で送らせる、の方が素直。

## 5. 分かっていないこと

## 8. 診断の道具

WSLからWindows側を調べる。**アプリの動作には触らない**(アプリを終了させる必要も無い)。

| コマンド | 何が分かるか | 触るもの |
|---|---|---|
| `npm run diag:hid` | WindowsのHID APIから見たCornixのインターフェース(用途・レポート長・開けるか)と、Vialの`[0xFE, 0x00]`への応答と往復時間。**アプリを通さない**ので、「OSでは動くのにアプリでは駄目」を切り分けられる | Vialのインターフェースに`[0xFE, 0x00]`を1回送る(アプリが接続時に最初に送るのと同じ) |
| `npm run diag:hid -- 3434` | 別のVIDの機器(例: Keychron)。`0xFF`が返ればVIAだけの機器 | 同上 |

注意:

- `scripts/diag/hid-probe.ps1`は**BOM付きUTF-8**で保存すること。Windows PowerShell 5.1はBOMが
  無いとShift_JISとして読み、日本語のコメントが化けて`param(...)`を巻き込み、引数が空になる
- アプリは`diag:hid`と同じWindowsのHID API(hidapi)で話す。`diag:hid`で答えるのに
  アプリで接続できなければ、アプリの側の問題
